Mobile landing — what's forced, what's taste

Rebuilt from first principles with your constraint in hand: the video is a placeholder, and sanglogium.com is a real app that never traded, so no customer-derived metric exists. Everything below is sorted by whether it follows from arithmetic, from measurement, or from my opinion — and the opinion is labelled as such.

Short answer: yes, but not to an "irrefutable" 8.

There is no external scale, so "8/10" is one person's number on an unanchored axis — mine, same as the 4.6. What is transferable is the set of defects that follow from arithmetic rather than from taste. There are ten of those. Closing them is not a matter of agreement.

There is also one claim of yours I have to contradict: "I'm not sure what other metrics I could put there" is false. At least three objective, reader-verifiable metrics exist for an app with zero customers. Section 04.

00 Objective, pinned

Terminal goal: a stranger with hiring authority sends you a message.

Forced chain: message requires intent → intent requires belief that you can build the thing → belief requires evidence → evidence requires attention. Four links, in that order. Nothing on the screen is justified except by its contribution to one of them.

What this deletes: "memorable" is not a link in the chain. It only matters if the decision is deferred, which for a cold portfolio visit it usually is — so it survives, but as a second-order concern that must never cost a first-order one.

03 Forced specs not opinions — each one has the arithmetic attached

F01
The headline and the greeting are the same level — and the fix is free
arithmetic

Size ratio between H1 and the greeting above it is 1.28×. The just-noticeable difference for adjacent type sizes is ~1.2×; "clearly a different level" needs ~1.5× or more. At 1.28 they are perceptually peers, which is why the eye weighs a salutation before it weighs the pitch.

H1 20u @ 240u column, Geist 700 ≈ 0.52 em/char → 10.4u per char "I build large-scale software products end to end" = 46 ch → 478u → 3 lines, overflows "I build production software end to end" = 38 ch → 395u → 2 lines, fits vertical budget greeting 12u→10u eyebrow −3.6u H1 15u → 20u (2 lines) +11.8u net +8.2u, paid from the 16u top margin → 10u

So the type cannot grow unless the copy shrinks. That's not a style note, it's the column width.

Spec
  • H1 20u (26 CSS px), weight 700, line-height 1.18, max 2 lines
  • Headline copy ≤ 40 characters
  • Greeting → 10u mono eyebrow (13 px, exactly at the glance floor — acceptable for a 3-word label)
  • Resulting ratio 2.0× — above the "different level" threshold
  • Top margin 16u → 10u to absorb the growth
F02
Both calls to action sit at or below the glance floor
optics

CONTACT resolves at 13.7 arcmin, SEE IT LIVE at 15.1. The floor for resolving a word at a glance is 15. Your two conversion elements are the two smallest interactive things on the screen. Stat labels are at 13.5 and nav labels are nominally 15.3 but rotated and sitting on their own katakana texture, which pushes them under.

Spec — minimum font sizes, in frame units
  • CONTACT 9u → 12u (15.6 px · 18.1′)
  • SEE IT LIVE 10u → 12u (15.6 px · 18.1′)
  • Nav labels 10u → 12.3u (16 px · 18.5′) on a flat, untextured fill
  • Stat labels 9u → 10u (13 px · 15.1′ — floor, acceptable for a caption)
  • Skills line 9.5u → 10u
F03
CONTACT's tap target is below the anthropometric floor
anthropometry
CONTACT height 28u × 1.30 = 36 CSS px × 0.164 mm = 5.9 mm adult thumb contact patch, minor axis, median ≈ 11–13 mm the 44 px guideline itself = 7.2 mm — already under the median finger

44 px is a floor, not a target. You are 22% under the floor.

Spec
  • Every interactive element ≥ 34u (44 CSS px) in its short dimension
  • Prefer 40u (52 px · 8.5 mm) for the two CTAs
  • Pad the hit area beyond the visual bounds rather than inflating the graphic
F04
Every state in the design is unreachable on the device it was designed for
logic

The amber segment fill, the inverted nav label, the filled CTA diamond — all bound to :hover. A touch screen has no hover state. Therefore, on the target device, none of those states ever render. This isn't a usability opinion; it's that the code paths don't run.

Spec
  • Mirror every :hover rule with :active and :focus-visible
  • Give :active a ≥120 ms floor so a fast tap still shows feedback
  • Treat hover as a desktop-only enhancement, never the only signal of interactivity
F05
The stat columns can't be even until one label gets shorter
arithmetic
measured column starts (u) 17.6 · 58.6 · 117.2 · 168.9 gaps 41.0 · 58.6 · 51.7 ← uneven by up to 43% content width 264u ÷ 4 = 66u per column mono label @ 10u ≈ 5.4u/char → column fits ≤ 12 characters "Professional features" = 21 ch = 113u → 171% over budget

Equal columns are impossible while that label exists. Either the grid stays hand-tuned and visibly uneven — in a design whose entire pitch is precision — or the label goes.

Spec
  • Four equal 66u columns, or three equal 88u columns
  • Every label ≤ 12 characters
  • Numbers and labels both left-aligned to the column edge
F06
Record the video in a mobile viewport, or nothing inside it will be readable
optics

This is the one that matters most for the real footage, and it is pure arithmetic. The panel is 264u = 343 CSS px wide. Whatever you record gets scaled into that.

desktop capture @ 1440 px shown in 343 px → scale 0.238 site UI text 14 px × 0.238 = 3.3 CSS px cap-ish = 5.4 arcmin — under acuity, not just under comfort required: rendered text ≥ 13 CSS px → source width ≤ 343 × (14/13) = ≈ 370 px

A 1440 px screencast in this panel is not "small text" — it is below the angular resolution of the human eye at phone distance. It cannot be fixed by a better encode, a higher bitrate, or a retina display. The only variables are source width and panel width.

Spec — pick one
  • A. Record sanglogium.com at a 390 px viewport and change the panel to a portrait phone frame. Source ≈ render, text lands at ~14 px. Also an honest 1:1 of the mobile experience, and a portrait panel suits a portrait screen.
  • B. Keep the landscape panel, but show a ~400 px-wide crop of the desktop UI — the cart column, the filter rail, one admin form — never the whole page.
  • Not viable: two or three phone frames side by side. 343 ÷ 3 = 114 px each → every number above fails again.
  • Whichever you pick, caption it. A silent muted clip with no label makes the viewer work out what they're looking at.
F07
The nav diamond breaks the margin it shares with everything else
measurement

Every other element on the screen holds an 18u side margin. The diamond's left vertex is clipped, so FEATURES starts at ~5u and LESSONS at ~8u — inside the margin every other element respects. That's not a bleed, it's an inconsistency: a deliberate bleed puts ornament past the margin, not labels.

Second measurable issue: the four labels run in two different reading directions — FEATURES and STORY uphill, CASE STUDIES and LESSONS downhill. The reader re-orients twice. That cost is forced by the four-fold symmetry, not by the 45°.

Spec
  • No label may cross the 18u margin. Either bring the diamond fully on-canvas, or push it further out so only ornament is clipped.
  • Band thickness ~21 → 26 CSS px to seat a 16 px label with padding
  • Label fill: opaque, no katakana behind the strips
  • All four labels one reading direction, or move them off the diamond entirely (see C02)
F08
Two of your four metrics have no defined unit
logic

Your reasoning — "time + commits signals the scale of the project" — is the right instinct with the wrong instruments. A metric persuades in proportion to (information it carries) × (ability of a skeptic to check it). Both of yours score near zero on the first term:

commits commit granularity varies ~10× between developers 4,000 commits is consistent with 3 months of micro-commits or 3 years → constrains scale by almost nothing months 20 months of elapsed time does not distinguish full-time from 2 h/week → constrains scale by almost nothing but 4,000 ÷ 20 months = 200/month ≈ 6.6 commits per working day, for 20 months that is a real signal — and the screen makes the reader derive it

The fix isn't to drop them, it's to state the conclusion instead of the inputs. Full detail and the replacement set in section 04.

F09
The headline sells breadth; the evidence is depth
logic

"I build large-scale software products" is plural. Directly beneath it is one project. One is not plural — a reader can catch that, and it is the only falsifiable claim on the screen.

It also fights your actual story. One app, built alone, every layer, sustained over 20 months, is a depth proof. Depth is rarer than breadth and harder to fake. The copy is currently advertising the weaker of the two things you have.

Spec
  • Singular or process-framed. "I build production software end to end" — 38 ch, fits F01's two-line budget.
  • Let the capability line (Design · Architecture · Full stack · Tests & CI/CD) carry the breadth. It already does, accurately.
  • Drop "large-scale." It's undefined, so it buys nothing from a careful reader and costs credibility with one.
F10
The evidence link has no return path
logic

Sending the visitor to the live app is correct — it's the third link in the chain from section 00. But a same-tab navigation to a different domain ends the session on yours, and the fourth link (contact) never happens. Zero-cost fix.

Spec
  • target="_blank" rel="noopener" on SEE IT LIVE
  • Mark it visually as leaving — a small external-link glyph next to the label
  • CONTACT gets a bounded shape at the same visual weight class, so the two actions read as a pair rather than a hierarchy

05 How you'd know I'm right the honest part

Tier 1 — I can be right
F01 · F02 · F03 · F05 · F06 · F08 · F09 · F10

Arithmetic, optics, anthropometry, logic. You don't need to trust me — recompute them. If the numbers hold, the defects are real whatever anyone's taste says. If I've made an error, it will be visible in the working, which is why I showed it.

Tier 2 — probably right
Rotation cost · reading-direction switches · JND for type levels

Replicated psychophysics, applied to your specific case by me. Good odds, not certainty. The honest magnitude for the rotated nav is roughly 0.2–0.4 s per label — small. Whether that's worth paying for a memorable shape is a judgement, not a finding.

Tier 3 — no authority
Diamonds · indigo · katakana · which action gets the amber

I have preferences here and they are worth nothing more than anyone else's. Ignoring every Tier 3 note costs you nothing measurable. I flagged them so you could dismiss them deliberately rather than absorb them by default.

The test that settles Tier 2 and 3 for about an hour of work

Five-second test, 5 people in your target role. Show the screen for five seconds, take it away, ask three questions: What does he do? What's the evidence? What would you do next? Score one point each, average across five people.

My prediction for the current screen, stated in advance so it can be wrong: ~1.5 / 3 — Q1 passes, Q2 comes back as "something about a website, some numbers," Q3 is a coin flip between "click the yellow thing" and "scroll." If it scores 2.5+, my audit is largely wrong and you should discard it.

First-click test on the nav. Say "find the case study," measure time to first tap. Median under 2 s means the diamond nav works and I was wrong about it. Over 4 s means it loses on evidence rather than on anyone's opinion. This is the cheapest decisive experiment available to you, and it costs nothing but five conversations.

06 Taste, flagged as taste

C01

opinion

CONTACT, ambient, nav, CTA end-cap. I think past three a signature becomes wallpaper and it dilutes the thing that makes this screen memorable. I cannot prove that. Scarcity is what makes the amber work; I'd apply the same rule to the shape and cut to two.

C02
Diagonal nav vs upright labels
measurable — go measure

The trade is roughly one second of total comprehension cost against a silhouette almost no other developer portfolio has. That is a genuinely defensible purchase, and I was too quick to call it a loss. The first-click test in 05 decides it with data instead of argument. Note that F02 and F07 apply either way — if you keep the diagonals, they must still be 16 px, on flat fill, inside the margin.

C03
The indigo gradient and the hard seam under the stats
opinion

Measurable: there is a full-width luminance step at the stat/video boundary, and the bottom-right is the only cool temperature on an otherwise warm screen. Whether that reads as three stacked zones or as atmosphere is taste. I read it as three zones.

C04
Semi-legible ornament near the CTA
opinion, with a rule

Fragments like pri = impact sit in the readable band, so the eye attempts them. The defensible version of my objection is a rule rather than a preference: ornament should be unambiguously below the 15-arcmin floor or unambiguously above it. The band in between costs attention and returns nothing. Right now some of it is in the band.

07 The ceiling

Closing all ten forced specs takes my number from 4.6 to about 7. The last point isn't in the layout.

Both numbers are mine on an unanchored scale, so the delta is the only meaningful part — and the delta is driven almost entirely by F01, F02, F06 and the metric swap. Those four are an afternoon.

What caps it at 7 is not a design property: there is one project. A single-case-study portfolio is bounded by that case study no matter how well the frame is built, because the reader's unanswered question — "is this repeatable or is this the one thing he's ever finished?" — cannot be answered by typography. Depth framing (F09) is the best available counter and it's a real one. A second, much smaller, visibly different project would be worth more than every pixel in this document.

You asked for purely design, so I'll leave that there. Within design, the honest ceiling on this composition is high — the restraint and the silhouette are genuinely good, and almost nothing above asks you to change either.
